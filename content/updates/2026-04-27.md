The LLMO project shipped its first public artifact this week. Two specification releases landed: v0.1.0, the initial publication on April 17, and v0.1.1, a follow-up on April 27 with clarifications to the signature format.

LLMO is a protocol for organizational identity on the AI-mediated web. Organizations publish a signed JSON document at `/.well-known/llmo.json` on their primary domain, declaring their canonical URLs, official channels, leadership, and other claims a consumer needs to evaluate trust. AI agents and language models verify the document's signature against the publisher's domain and use the resulting claims as authoritative. The protocol does not impose a central trust authority; trust judgments remain the consumer's responsibility, but the canonical location and cryptographic binding are now there.

## What v0.1.0 introduced

The initial release defined the protocol's substrate. A schema for the document. Two conformance tiers, Standard and Strict, with progressively stronger requirements. A signing model based on JSON Web Signatures over JSON Canonicalization Scheme (JWS over JCS, RFCs 7515 and 8785). A worked example showing a real organization's document end-to-end. A reference test vector set so implementers can verify their tooling against the spec.

The specification is at [/spec/v0.1/](/spec/v0.1/), with the schema at [/spec/v0.1/schema/](/spec/v0.1/schema/) and the reference test vectors at [/spec/v0.1/test-vectors/](/spec/v0.1/test-vectors/). Both the spec text and schema are versioned and immutable once published; future changes will land as v0.1.x patches or v0.2 onward.

## What v0.1.1 fixed

The v0.1.1 release on April 27 closed two gaps surfaced during early implementation review. First, the JWS profile was tightened to require the standard attached form per RFC 7515; detached-payload variants per RFC 7797 are now explicitly prohibited. The on-disk shape of the `signature` field is unchanged, so documents already conforming to v0.1.0 in standard mode remain conforming. Second, a new section flagged post-quantum cryptographic readiness as an open question for future versions; ES256, ES384, and EdDSA remain the registered algorithms for v0.1, with PQ migration deferred to a future LIP.

The v0.1.1 changelog entry is at [/spec/changelog/](/spec/changelog/).

## What is happening next

Implementers at this stage are working from the spec, schema, and reference vectors. A reference command-line tool was published shortly after v0.1.0 (see the [Deploy page](/deploy/) for installation). A web-based validator runs at [/validator/](/validator/) for direct paste-or-URL verification. The first LIP, [LIP-1](/spec/lips/lip-0001/), defines the proposal process for changes from v0.2 onward.
