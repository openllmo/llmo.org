The biggest shipping week of the project so far. A specification release, a tooling release, and a set of operational decisions that change how the project's automation runs going forward.

## v0.1.5: Per-claim signature verification

The v0.1.5 specification release on May 5 added rule X6 to the Strict-tier conformance set: per-claim signatures, not just the document-level signature. Until this release, the project's signing model had two layers in theory (document-level and per-claim) but only the first was a normative conformance rule; per-claim signatures could be present but were not required to verify. v0.1.5 closes that gap. A publisher who attaches per-claim signatures must ensure each one verifies against a key in the publisher's JWKS. Documents with no per-claim signatures pass X6 trivially; documents with at least one per-claim signature must have all of them verify.

The release also relabeled the conformance rules to match what validators emit. Standard-tier rules now have explicit S1 through S6 labels; Strict-tier rules have X1 through X6. Prior unlabeled bullets created cross-reference drift between spec text and validator output, where a reviewer reading "S4 failed" had to count bullets in the spec to find which rule.

The project's own `llmo.json` document was re-signed in a parallel ceremony to gain a per-claim signature on its disavowal claim, exercising X6 end-to-end as the protocol's first publisher. Full details in the [v0.1.5 changelog entry](/spec/changelog/#015---2026-05-05).

## CLI v0.1.5 published to npm with provenance

The reference command-line tool (`llmo`) was published to the npm registry as v0.1.5, with SLSA v1 provenance attestation attached at publish time via OIDC trusted publishing. Users running `npm install -g llmo` now get the version that supports per-claim signing and verification, plus the full ES256/ES384/EdDSA algorithm matrix that the spec permits.

The package is at [npmjs.com/package/llmo](https://www.npmjs.com/package/llmo). The provenance attestation is visible in the package's npm metadata, providing a cryptographic chain from the tag in the cli repository through the GitHub Actions workflow that built and published it.

## Branch protection and scheduled workflows

This week the project's main branch became protected with no admin bypass. All changes now land via pull request with passing CI; the editor is subject to the same workflow as any contributor. Two scheduled workflows landed alongside: a Monday weekly digest summarizing repository activity, and a Sunday audit checking six classes of static-state drift (URL resolution, registry consistency, anchor resolution, cross-document references, and JWKS publication freshness).

The scheduled workflows produced an unexpected substrate problem: pull requests created by the default workflow token do not trigger required-check workflows on the resulting PR (a GitHub anti-recursion safeguard). Required checks never fired, auto-merge never resolved, and the PRs sat open. The project resolved this by registering a dedicated GitHub App (`llmo-workflow-bot`) under the openllmo organization. PRs created via the App's installation token do trigger workflows, so the scheduled-cron path now operates end-to-end without operator intervention.

The decision to use a GitHub App rather than a Personal Access Token or `pull_request_target` trigger is recorded in [ADR-0004](/adr/0004-github-app-workflow-auth/) with the alternatives explicitly considered.

## Three new ADRs

The Architecture Decision Record set grew from two to five this week. The new entries backfill operational decisions that previously lived only in the project's BACKLOG file:

- [ADR-0002](/adr/0002-branch-protection-on-main/): Branch protection on main, with no admin bypass.
- [ADR-0003](/adr/0003-backlog-discipline-track-conventions/): BACKLOG discipline and Track conventions, with CI enforcement.
- [ADR-0004](/adr/0004-github-app-workflow-auth/): GitHub App for workflow PR creation.

Each captures why-this-not-that for a decision that affects how the project is run, so future stewards inherit the rationale rather than re-deriving it from commit history.

## ES384 and EdDSA test vectors

The reference test vector set at [/spec/v0.1/test-vectors/](/spec/v0.1/test-vectors/) gained two new strict-tier vectors covering the ES384 and EdDSA signature algorithms permitted by §4.2. The original three vectors covered only ES256; the new vectors complete coverage so implementers can verify their tooling against the full algorithm matrix the spec permits.
