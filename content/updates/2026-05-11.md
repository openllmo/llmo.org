The week opens with the biggest single-day spec growth so far. v0.1.7 caught up on three days of drift; v0.1.8 added the substrate signals that downstream commercial scoring needs; two new ADRs documented the patch policy and the deployment model the spec assumes; and a [/glossary/](/glossary/) page lands as the controlled vocabulary the builder agent will normalize against.

## v0.1.7: catching up on what shipped without a release cut

Between v0.1.6 (May 8) and this week, substantive work merged but accumulated in the changelog's `[Unreleased]` section without a release cut: a comprehensive test-vector expansion covering every v0.1 conformance rule, ES384 and EdDSA strict-tier vectors completing the algorithm coverage, and a simplification of the spec's Appendix B (replaced with a pointer to the standalone changelog to eliminate drift between two version-history sources).

The cut from `[Unreleased]` to `## [0.1.7] - 2026-05-11` was the recovery. Mechanically it was small; what matters is the policy that made it necessary and the automation that prevents recurrence. Both lived only in conversation history before this week. The full v0.1.7 contents are in the [changelog entry](/spec/changelog/#017---2026-05-11).

## v0.1.8: additive growth on schema and claim types

v0.1.8 is purely additive over v0.1. Every conforming v0.1 document validates against the v0.1.8 schema unchanged. The schema URL and the `llmo_version` value are both unchanged; only the schema's contents grow.

Six new core claim types land in §3.5:

- **`contact_points`**: typed contact addresses (billing, security, abuse, legal, press, support, phone, messaging) with optional verification metadata. The schema enforces "if verified, proof and timestamp are required" via `if`/`then`, so reference implementations get the constraint for free.
- **`categories`**: schema.org Organization subtype URIs plus NAICS codes. No trademarked third-party taxonomies.
- **`locations`**: postal address, WGS84 coordinates, service area (radius, polygon, bounding box, or named places), business type, per-location publisher identifier.
- **`hours`**: regular weekly schedule, calendar exceptions, named alternate sub-schedules (drive-through, kitchen, brunch). Time format is 24-hour `HH:MM` with `24:00` permitted as a close time only.
- **`attributes`**: open map of canonical attribute names to typed values. Names SHOULD come from the controlled vocabulary at [/glossary/#attributes](/glossary/#attributes).
- **`operational_status`**: open, opening soon, temporarily closed, permanently closed; effective date required for any non-open status.

Five new optional top-level fields land too: `revocation_registry`, `dns_corroboration`, `publication_history`, `delegates_to`, `delegated_from`. Forward-compatibility pointers; their wire formats are deferred to later patches.

The entity object becomes more expressive. `entity.name` accepts an array of `{name, locale, primary}` entries for internationalized names (with the schema enforcing exactly one primary via `contains` and `minContains: 1, maxContains: 1`). External identifiers gain a structured verification form alongside the v0.1 plain-string form: `wikidata`, `duns`, `lei`, `did`, plus a new `irs_ein` well-known key, all carry `{value, verification_method, verification_proof, verified_at}` when the structured form is used.

Three conditional constraints that earlier versions would have left to validator code are encoded in the schema itself (Draft 2020-12 `if`/`then`, plus `contains` with cardinality bounds). The schema is the source of truth; reference implementations inherit the checks via schema validation rather than reimplementing in two places.

Six top-level field names are reserved (`posts`, `reviews`, `qa`, `media_pointers`, `advertising_extensions`, `consumer_metadata`) in a new §3.8 as documentation-only forward-compatibility slots. Each maps to a real entity-data category drawn from incumbent production systems; future versions may define them with concrete schemas, at which point the reservation becomes binding.

Full v0.1.8 detail in the [changelog](/spec/changelog/#018---2026-05-11) and the [spec text](/spec/v0.1/).

## `provenance_markers` on the claim envelope

A small addition with outsized framing implications: every claim now has an optional `provenance_markers` array (strings). The builder agent (see ADR-0007 below) populates these with markers recording how it derived each claim: `source:publisher-website`, `cross-validated:wikidata,gmb`, `human-reviewed:2026-05-11`. The markers live inside the signed payload by design; consumers MAY use them as advisory signal for confidence calibration but MUST NOT treat them as authoritative.

This is the agent's per-claim audit trail. The protocol's existing `confidence` enum (authoritative, advisory, provisional) is publisher self-rating; `provenance_markers` is the agent's "here is how I built this" trail visible to every downstream reader.

## /glossary/ as the agent's normalization layer

The [/glossary/](/glossary/) page is new this week. Four sections:

1. **Protocol terms**: 39 entries covering the technical vocabulary the spec uses (claim, claim envelope, JWS, JCS, JWKS, tier rule, TOFU, trust anchor, conformance tiers, and the rest).
2. **LLM background terms**: 6 entries for human readers new to the LLM context the protocol assumes (Agent, Grounding, Hallucination, Inference, LLM, RAG).
3. **Attribute vocabulary**: 24 canonical attribute names with type indicators, cross-referenced from Google Business Profile, Yelp, Bing Places, and Apple Business Connect.
4. **Standards referenced**: 22 external standards LLMO inherits from or pairs with (RFCs, ISO codes, well-known identifiers, adjacent protocols), one line each.

The attribute vocabulary is load-bearing: it is the builder agent's normalization layer. Without a canonical normalization target, every implementation invents its own ("free wifi available" / "wireless internet" / "guest network") and consumers cannot answer entity queries reliably across publishers.

## Two new ADRs

[ADR-0006](/adr/0006-version-bump-and-release-cut/) records the v0.1.x patch policy formally: in-place schema updates at the canonical URL, additive-only patches, `llmo_version` stays at the minor-version identifier across all patches, releases cut from `[Unreleased]` via an explicit script invocation rather than as a merge side effect. The policy was implicit before this week; the three-day documentation drift that preceded the v0.1.7 cut surfaced the gap.

[ADR-0007](/adr/0007-claude-as-builder/) codifies the architectural framing the v0.1.8 work assumes: LLMO documents are assembled by an LLM agent on the publisher's behalf via an API plus wizard interface, not authored by the publisher by hand. Publisher input is bounded to an email of record, consent, and targeted review. The agent queries public sources, normalizes via the glossary, structures under the schema, and tags each claim with `provenance_markers`. Future protocol design decisions apply two tests: what does the consumer LLM gain from this field, and what does the builder agent need to populate it from public sources or surface as a minimal wizard question.

## Release-cut automation

`scripts/cut-release.sh` lands alongside ADR-0006. The script validates inputs (semver-shaped version, ISO date), refuses to overwrite an existing version section, idempotent against an empty `[Unreleased]`, and prints a single line naming what it did. First in-PR use cut v0.1.8 from `[Unreleased]` to `## [0.1.8] - 2026-05-11`. A bug surfaced on the first run (an idempotency-check awk script printed twice and the shell mis-read the result); fix bundled into the same PR. v0.1.9 and onward will cut via the script with no manual editing of the changelog.

## What is happening next

Three explicit follow-ups from v0.1.8, all filed in BACKLOG:

1. Reference validator update to handle the six new claim types and the new claim-envelope `provenance_markers` field. Schema validation against AJV already works; the validator's per-claim UI dispatch needs to catch up to render the new types with full fidelity.
2. Positive and negative test vectors for the v0.1.8 schema additions. The existing 31-vector v0.1 set passes back-compat against v0.1.8 as the hard check; the new schema additions need their own coverage.
3. Attribute vocabulary curation cadence. The seed is 24 entries; production publisher data will surface attributes the seed does not cover, and a periodic review cycle keeps the vocabulary aligned with what the builder agent actually encounters.

The CLI's vendored schema needs a v0.1.8 re-vendor in a paired PR on `openllmo/cli`. Both reference implementations (validator and CLI) need to land before external implementers can reasonably build against v0.1.8.
